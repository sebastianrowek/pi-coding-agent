# Phase 6 Implementation Notes

Status of the Phase 6 implementation (NDJSON run logging + rich rendering + prompt surface, per PHASE6.md).

## What was built

- `logging.ts` (new) — `newRunId()` (timestamp + 2-byte hex suffix), `DEFAULT_LOG_DIR`, `createRunLogger()` (mkdir recursive + **eager file creation with flag `"wx"`**, so an unwritable directory throws at setup and a run-id collision retries up to 3 times instead of two runs sharing a file), `RlmLogger` (promise-chain write queue, disable-on-first-write-failure with exactly one `warn`, `close()` flushes and drops later events, `log()` never throws — even `JSON.stringify` failures are swallowed), the `RlmLogEvent` union (run_start / turn_start / assistant_text / code_block / exec_result / rpc / nested_start / nested_end / downgrade / run_end), `preview()` (capped JSON with `String()` fallback), and `loggingOnEvent()` (InvestigatorEvent → log adapter that skips `done` and always forwards to `next`). **Caps are applied centrally in `log()`** (`text`/`code`/`answer` → 20 000, `prompt`/`argsPreview`/`resultPreview`/`error` → 500) so no call site can forget them; PHASE6.md's sketch had the caps at the call sites.
- `rpc.ts` — `RlmRecursionOptions` gains optional `inv` (default `"root"`) and `logger`; `NestedEvent` extracted as a named export (was an inline type; index.ts and tests reuse it). `withRpcLogging()` wraps every handler (plain or entry) with the timing decorator when a logger is present; `rpcResultChars()` records payload size next to the 500-char preview. `runNestedRlmQuery()` gains a `nextChildInv` parameter: the per-handler-set counter lives in the `createRpcHandlers` closure, and the id is allocated **synchronously after the downgrade check**, so sibling ids reflect call order and downgrades never consume an id. Downgrades log a `downgrade` event before delegating to the analyst; `nested_start` logs where `onNested({phase:"start"})` fires; `nested_end` rides the existing `emitEnd` guard (no-double-emit and error-path coverage carry over). Child handler sets get `{ ...rlm, depth: childDepth, inv: childInv }` and child runs get `onEvent: loggingOnEvent(rlm.logger, childInv)` — child turn detail goes to the log only, per locked decision 5.
- `index.ts` — new `logDir` param. The flat `transcript: string[]` was replaced by `createTimelineRecorder()` (exported, pure, testable): `TimelineEntry { kind, turn?, depth?, text }`, per-entry cap 2 000, total cap 200 **including** the dropped-note marker (199 real + 1 note once dropping starts), `entries()` returns a fresh array each call so streamed details snapshots cannot alias the live buffer. `timelineToText()` (joins entry texts with `\n\n`, byte-identical to the old transcript format) and `formatRunStats()` are exported pure helpers. Logger lifecycle: created right after param/model validation (failure → one `note` + logger-less run, same philosophy as the kb_search degradation; the logger's own mid-run `warn` lands through the same `note` path), `run_start` after the context search, `run_end` through a once-guard on the success path and in the catch (`aborted` when `signal?.aborted`, else `error`), `await logger.close()` in `finally` before `repl.close()`. `details` gains `runId`/`logPath`/`timeline`. `promptSnippet` + 3 `promptGuidelines` bullets added. `renderCall` = bold tool name + 80-char prompt preview + one muted line listing only non-default params (scope/k/maxTurns/maxDepth/maxBudget/models). `renderResult` = partial (⏳ header with turn/calls/nested + last 8 timeline entries), collapsed (status icon by stopReason — ✓ final, ◐ no_code/max_turns/budget, ✗ error/aborted — + `formatRunStats` + first 10 answer lines + Ctrl+O hint), expanded (Container: header, `─── Investigation ───` styled timeline with nested markers indented by depth, `─── Answer ───` as Markdown, dim `run <id> · log: <path>` footer), and a plain-content fallback when `details.timeline` is missing (old sessions). `renderShell` stays default.
- `test-phase6.ts` (new) — 15 tests: 6 logger-level (creation/distinct ids, order + round-trip + ts, 50 interleaved concurrent writes, central capping for text and preview fields, creation-throws + write-failure-warns-once degradation, close-flush + post-close drop), 5 wiring-level with the real REPL + fake completeFns (loggingOnEvent mapping with `done` skipped and `next` unbroken, RPC ok/failure logging incl. previews/durations/resultChars, two-child nested run with `root.1`/`root.2` in call order + child turn events + one shared run id, downgrade event without nested_start under a deep inv id, no-logger reruns of both wiring scenarios with identical behavior and an empty temp dir), 4 formatter/render-level (recorder kinds/caps/overflow + onChange counts, timelineToText format, formatRunStats full/minimal, render smoke for call/collapsed/partial/expanded/fallback/icons).

## Review fixes (post-implementation)

- `logging.ts` — `question` added to `TEXT_CAP_FIELDS` (20 000-char cap). It was the one free-text field `withCaps` did not cover, and it comes straight from the calling agent (`params.prompt`) with no bound, so a pathological caller could put an arbitrarily large prompt into the `run_start` line. PHASE6.md's cap table had the same omission — the central-caps refactor was supposed to make exactly this class of gap impossible, so the fix belongs in the cap list, not at the call site. Test 4 extended to cover it (15/15 still green).

## Notes / deviations

- PHASE6.md test 8 said "handlers built with a logger and a mock `kb_search`" — the `kb_search` handler calls the real `kbSearch` (not injectable, unlike `kbSearchFn` which only feeds child context searches). The test covers `ok: true` RPC logging via `llm_query` (injectable `completeFn`) and `ok: false` via `kb_search` against a nonexistent binary (`execFile` rejects fast); the Python traceback still reaching the block proves logging is observability, not behavior.
- Test 15 (render smoke) worked headlessly, including the **expanded** view: `initTheme("dark")` initializes the global theme that `getMarkdownTheme()` needs, and pi-tui components render to plain lines via `component.render(width)`. The PHASE6.md fallback (manual-only verification) was not needed; tmux verification of the live TUI remains open below.
- In the `renderResult` tool callback, `TDetails` is `unknown` (the registerTool generic does not flow into the render callbacks), so the result is cast to `AgentToolResult<RlmQueryDetails | undefined>` — same pattern as the subagent example's `result.details as SubagentDetails | undefined`.
- `formatRunStats` omits `nestedRuns` when it is 0 (falsy check, matching the subagent's usage-stats style); `turns`/`contextHits` are always shown, `modelCalls`/`costUsd` only when present.
- The nested-prompt preview in the timeline stays a plain 120-char head slice (Phase 5 rationale: `capText`'s head+tail format would inject newlines into a single marker line).
- `run_end` on the catch path logs no `answer` (there is none); turns fall back to `recorder.lastTurn()`.
- `createRunLogger` creates the NDJSON file eagerly, so a "file exists but is empty" state is possible for runs that crash before `run_start` — accepted; `run_start` is otherwise always the first line.
- Accepted gap (same family as the late-settling-handler drop): if the logger's first write failure happens during the `close()` flush in `execute()`'s `finally`, the disable warning's `recorder.note` fires after the result's `details` snapshot was taken, so it appears only in a trailing `onUpdate` that the final render replaces — invisible in the persisted result. Logging failures at the run boundary are silent by design.
